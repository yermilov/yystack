Moved verbatim from `SKILL.md` on 2026-10-02: the dated measurements and war stories behind each one-line ruling that stays in SKILL.md «Common landmines». Read when a ruling there does not cover what you are seeing, or before arguing with one.

## AUP — subagent option (history)

**Subagent option, deprecated.** Earlier versions of this skill ran Phases 1–4 in a `general-purpose` subagent specifically to isolate AUP risk. The tradeoff went against it: long opaque waits, no mid-flight visibility for the user, structured-return parsing overhead, and when a refusal fires inside the subagent the synthesis is typically lost while the raw rounds survive. The skill no longer does this by default. If a particular run keeps hitting refusals despite the hygiene above, offering the user a subagent run for that question is still a valid escape hatch — just not the default path.

## Other landmines

**Gemini bleeds in cross-session memory; ChatGPT new chat is sterile.** Gemini Pro has chat history enabled by default and will reference details from earlier conversations even when you start a fresh chat — sometimes helpfully (carrying over context the user gave it earlier), sometimes wrongly (filling in specifics from old chats that don't apply to the current question). In a real run Gemini named a specific product model in a Round 1 answer although the prompt only named the general category — the identifier came from an earlier chat in the same account. ChatGPT does NOT do this in fresh chats by default. Two implications: (a) when comparing Round 1 outputs, Gemini's "extra specificity" may be hallucinated continuity, not real reasoning — verify before trusting it; (b) when the user asks a question where you DON'T want any prior framing leaking in (e.g. testing whether models converge from scratch), explicitly tell Gemini "ignore prior context, answer this from scratch" or just open ChatGPT-only for that round.

**Bridge content filter blocks DOM dumps containing `key: "value"`.** Any TypeScript object literal, JSON snippet, or anything that pattern-matches a cookie string gets blocked when extracted via `javascript_tool`. Workaround: take small slices and stitch around the blocked chunks. ⚠️ Older revisions suggested falling back to `body.innerText` here; prefer `get_page_text` (last `div.markdown` on ChatGPT, last `model-response` on Gemini) — `body.innerText` silently truncates long answers (~3.6k of a 26k answer, measured 2026-08-23) and freezes mid-stream on Gemini, so it trades a visible block for an invisible one.

**Bridge truncates JS return values around 1500 chars for Cyrillic content.** This is separate from the content filter above — it's a hard byte limit on the response payload. Latin text gets ~1500 chars per slice; Cyrillic (UTF-8 2 bytes/char) gets cut at ~750 visible chars. Practical pattern: store the full response in `window.__resp = …` once, then extract via repeated 1000-char `slice(start, end)` calls. After the first 1000-char slice you may see a `[TRUNCATED]` marker — drop that, take the next slice from where the _unmarked_ text ended, not where you asked. For large responses (40k+ chars), build a section-offset map first by regexing on `\n\d\. ` headers, then sample only the load-bearing sections. **Write the assembled full text to disk immediately and synthesize from there**, not from the in-chat slices.

**⚠️ ChatGPT chat responses are NOT reliably readable via `[data-message-author-role]` — use `get_page_text`.** An earlier version of this skill said a Thinking-tier response sits in those divs "accessible via plain `innerText`". **Measured 2026-08-22 that is false, and it is the dangerous kind of false:** on two separate COMPLETED GPT-5 answers, `[data-message-author-role="assistant"]` returned **372 characters — the citation chips alone** (`PubMed`, `Oura Support`, `Sleep as Android`…), while the full multi-thousand-word answer was rendered on screen. `el.querySelectorAll('p')` inside that same element returned **1**, and `innerHTML` was 34 KB of chip markup. A run that trusts the selector concludes the council returned nothing and reports a failed council — which is exactly what nearly happened. **`get_page_text` returns the whole answer**; make it the default extractor for chat-mode responses and keep the clipboard pattern for Deep Research only. This is the general "confirm the instrument" rule in its nastiest form: a suspiciously empty result is a claim about your INSTRUMENT until a second instrument disagrees.

⚠️ **And `document.body.innerText` has the same failure with a different number — it TRUNCATES rather than empties, which is far harder to notice.** Measured 2026-08-23: it stalled at ~3.6k characters on an answer that was actually **26k**. A truncated read looks like a complete short answer; nothing marks the cut. Read the **last `div.markdown`** instead, and on a long answer build a heading-offset map so you can pull sections without re-reading the whole thing.

**GPT-5 «Pro» tier can hang indefinitely; «Високий» (High) is the working default for council runs.** Measured 2026-08-22: both council questions sent at Pro browsed extensively (27 and 23 websites, one downloaded a PDF study), emitted a reasoning trace, and then produced **nothing for ~2.5 hours** — stop-button still present, trace frozen, zero assistant output. Reloading the conversation URL, the documented websocket recovery, did not help. Re-sent at High, both returned complete, densely-cited answers in **3–4 minutes**. So: run council prompts at High; reach for Pro only if High's answer is visibly thin, and never let a Pro run block the whole task — you can re-ask at High in a fresh chat and lose only minutes.

**The ChatGPT model control is now a reasoning-effort SLIDER, not a model dropdown.** The composer shows the current tier as a word (`Pro`, `Високий`, …). Clicking it opens a small popover holding the slider plus a «Додатково ›» link; click/drag left of the knob to lower the effort. The setting **persists into new chats in the same browser**, so set it once per session. There is no «GPT-5 Thinking» menu item to hunt for any more — don't waste a screenshot looking for one.

**`?q=` URL pre-fill works on ChatGPT and NOT on Gemini — the split matters, so don't apply either half to the other.** An earlier version of this file called it dead on *both* after a 2026-08-22 run; **re-measured 2026-08-23 that is wrong for ChatGPT**, and two independent sessions found the same thing. On `chatgpt.com/?q=<ENCODED>` the prompt does land in the composer (with a short delay — check the composer, don't judge on the first screenshot). On `gemini.google.com/app?q=<ENCODED>` it genuinely does nothing: the composer stays at `innerText.length === 1`. So: keep the URL path for ChatGPT, type into the real editor for Gemini.

⚠️ **After a `?q=` navigation, strip the QUERY STRING but keep the real path** — otherwise the whole encoded prompt keeps echoing back through every Tab Context read (~1.2k tokens per read, for the rest of the session):

```js
history.replaceState({}, '', location.pathname);
```

Do **not** replace the pathname with a made-up one like `/c/x`: once ChatGPT has redirected to the real conversation URL that path is what the reload-the-conversation recovery below depends on, and a fabricated one breaks it.

**The conversation URL is the durable handle; the tab is not.** Chrome closed the entire MCP tab group out from under the session mid-run, and `Runtime.evaluate` timed out at 45 s repeatedly while long generations were open. Both conversations survived server-side. **Record every `/c/<id>` URL as you create it** and recover by navigating back to it — never by re-asking the question.

**Gemini IS driveable — a 2026-08-22 entry here declared it "logged in and still undriveable" behind an extension site-permission wall, and that did not reproduce on 2026-08-23 in the same browser and profile**, so the claim has been removed rather than argued with.

What the 2026-08-23 run measured instead is below. ⚠️ **Scope it as one host on one date, not as Gemini's permanent contract** — the two runs a day apart disagreed, which is itself the reason to distrust any standing claim here. Treat each item as the *verified working method* and the first thing to try, not as the only thing that can possibly work; if a submission path outside this list works for you, that is new evidence, not a violation.

- **Enter did not send, and a `ref`-based click on the send button silently no-opped.** What did submit was a **`computer` click on coordinates taken from a screenshot captured AFTER the text is in place** — the button moves as the composer grows, so a coordinate from an earlier screenshot misses. Reach for that first.
- **`type` silently swallows `\n`.** `рядок один\nрядок два` arrives as `рядок одинрядок два`. Send multi-paragraph prompts as separate `type` calls with `shift+Return` between them — or, simplest, **write the prompt as ONE paragraph with no newlines at all**, which needs neither the clipboard nor `javascript_tool`.
- **Right after `navigate`, the composer can drop every space and digit** while `type` still reports success. Read the composer back before submitting; never submit on the strength of a success return.
- **All three progress indicators freeze while the answer is still streaming** — `body.innerText.length`, `model-response.innerText`, and the Stop-button selector (which stays truthy after completion). `get_page_text` is the only reliable reader; take the LAST `model-response` element.
- An **empty** `model-response` for several minutes on a follow-up turn is a stall, not the Pro-tier hang documented above: reload the `/app/<id>` URL.
- ⚠️ **`computer` with `action: "type"` IGNORES its own `tabId` and types into whatever tab is
  foreground.** Clicks and screenshots respect `tabId`; `type` does not (measured 10.09.2026,
  gygylyna task `b443a7a4`). Text meant for a Gemini tab landed in the ChatGPT composer twice in one
  session, and the whole cross-round council never happened because of it. Before any `type` call in
  a multi-tab council, confirm the TARGET tab is actually focused/foreground, and **read the
  composer back** before submitting.

⚠️ **On one sandboxed cloud host (2026-08), `execCommand` injection was refused by a safety classifier — and the refusal poisoned the session:** every later batch containing page-script calls was blocked for the rest of the run. So on such a host, do not reach for the injection fallback at all; the one-paragraph `type` path above is what works there.
⚠️ And know the trap next door: a machine's *other* connected browser may drive gemini.google.com perfectly well — because it is signed into **a different person's account**. Running a council through it would spend someone else's quota on this user's question. Check whose account it is before treating a second browser as the fix.

**Gemini's submit button gets stuck after a Stop click.** When you press Stop on a still-streaming response and immediately try to send a new prompt, the button stays in "Зупинити відповідь" mode. **Recovery:** navigate to the same conversation URL (it preserves the conversation history) and re-send the prompt — submitting via a **coordinate click on a screenshot taken after the text is in place** — the verified method above. (An earlier version of this line said "press Enter"; Enter did not submit in the measured run.)

**ChatGPT Plus DR can fail mid-flight after 30–60 min.** Symptom: report card shows «Не вдалося виконати дослідження» with all plan items unchecked. **Recovery:** click «Змінити модель» icon (5th of 6 action icons), then «Повторити спробу • 5.5 Thinking» in the popover, then «Почати» on the re-shown plan. Retry is usually faster than the original (cached search context). Don't auto-retry a second time without telling the user. Real-run total: ~50 min fail + ~25 min successful retry = ~75 min wall clock for one ChatGPT Plus DR.

**ChatGPT DR report sits in a cross-origin iframe.** This is the single most surprising landmine for someone who has only used Gemini before. `document.body.innerText.length` stays at ~3000 chars _no matter how big the report_ — the report is rendered inside `<iframe title="internal://deep-research">` which is CORS-isolated. JavaScript extraction is impossible. Use the clipboard pattern: expand to fullscreen → triple_click in iframe → cmd+a, cmd+c → the host's clipboard-read capability. Don't waste time trying to find a JS workaround — there isn't one. Step-by-step in `references/ui-tactics.md` §5b.

**Streaming completion is not just "stop button gone".** Both UIs sometimes leave the stop button visible after generation completes; conversely, length can plateau during DR phase transitions while the stop is still active. On **ChatGPT**, combining the two (length stable ~10s AND stop-button selector empty) is still a workable test. On **Gemini it is not** — both halves were measured unreliable on 2026-08-23 (see the per-platform note above), so read the last `model-response` with `get_page_text` and judge completion from the content.

**Gemini sometimes serves an A/B experiment («Яка відповідь корисніша?») with TWO answers — and `innerText` shows you neither.** Measured 2026-08-22: `document.body.innerText` froze at ~1700 characters while `document.querySelectorAll('message-content, model-response')` returned both variants in full. So the familiar symptom — a response that will not grow — has a second cause besides a stalled stream, and the two look identical from `innerText` alone. ⚠️ **Do not pick one and discard the other: the disagreement is free cross-pressure material.** In that run the two variants contradicted each other (two different numeric limits for the same rule, in two currencies) and **each contained exactly one error** — so keeping both and pushing on the divergence produced a better answer than either variant, and no extra round was needed to get it. Capture both, attribute them separately in the brief, and feed the contradiction into Round 2 rather than resolving it yourself.

**Gemini Pro Thinking can hang indefinitely on follow-up «продовжи» turns.** Symptom: you ask Gemini to continue from a truncated section, the streaming indicator appears, the second response container shows up empty (length 0), and the tab eventually stops responding to CDP `Page.captureScreenshot` (timeout after 30s). This isn't a council failure — it's a Gemini-side issue specific to long Thinking generations on continuation turns. **Recovery:** don't keep waiting. If you have ChatGPT's full response and substantive convergence on the spine, synthesize from what you have and note the partial Gemini coverage in the brief. The marginal value of Gemini's missing sections is rarely worth a 10-minute wait that may never resolve.

**CDP `Runtime.evaluate` 45-second timeout.** When the prompt loop in JS does `for (label of labels) await createLabel(...)` over 16+ items, the whole batch can exceed the bridge's 45s evaluation cap and you'll get «Runtime.evaluate timed out». Recovery: navigate-and-recheck — the items that completed before the timeout did stick (they fired actual network requests). Re-run the loop with the remaining items only. **Prevention:** keep any single `javascript_tool` call under ~25 seconds of expected work; split into multiple calls with explicit waits between if longer.
